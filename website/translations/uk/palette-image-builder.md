# Створення власного образу Modalix

Palette Image Builder (PIB) створює власний образ eLxr для Modalix. Він постачається як окремий контейнер Docker, який підтримується в репозиторії Palette SDK. Встановіть його через sima-cli; основний контейнер SDK не потрібний.

Один проєкт створює два формати розгортання:

- **`.swu`**: підписаний пакет оновлення для працюючої плати.
- **`.img.gz`**: повний образ диска для початкового налаштування або відновлення.

## 1. Встановіть PIB

Після встановлення [sima-cli](https://docs.sima-neat.com/getting-started/installation) і Docker виконайте:

```bash
sima-cli neat install sdk/pib
pib doctor
```


Інсталятор завантажить контейнер для x86_64 або ARM64 та встановить команду `pib` у Linux, macOS чи Windows. Якщо PATH змінено, відкрийте новий термінал. PIB працює в Linux-контейнерах: Docker має бути запущений і дозволяти привілейований доступ для складання образів. На хості x86 емулятор ARM64 входить до складу контейнера та налаштовується автоматично.

У локальній теці проєкту потрібно щонайменше 10 GiB вільного місця для `minimal` або 20 GiB для `palette`, а також приблизно стільки ж у сховищі Docker. Під час збирання потрібний доступ до репозиторіїв пакетів Debian/eLxr і SiMa. Образ для плати має архітектуру ARM64.

`sdk/pib` вибирає останній опублікований пакет main. Іншу гілку чи випуск SDK можна вибрати за тим самим синтаксисом, наприклад `sima-cli neat install sdk/pib@develop`. Ручне встановлення через Docker та вимоги до хоста наведені в [довіднику зі встановлення](palette-image-builder-reference.md#installation).

## 2. Створіть проєкт образу

```bash
pib init my-image --flavor minimal
cd my-image
```


Використовуйте `--flavor palette`, якщо потрібне графічне середовище та більший набір пакетів. Платформний випуск образу визначає вибраний контейнер. Проєкт містить:

```text
my-image/
├── image.yaml       # version and customizations
├── custom-debs/     # your ARM64 or architecture-independent Debian packages
├── overlay/         # files to add to the root filesystem
├── hooks/           # optional post-install scripts
├── keys/            # your signing identity and public trust material
├── configs/         # release-specific board defaults; normally leave unchanged
└── out/             # generated artifacts
```


Наступні команди виконуйте з теки проєкту. Команда `pib shell` відкриває оболонку з підключеними файлами проєкту. Усередині неї запускайте `pib` безпосередньо; команда `exit` повертає до хоста.

Для робочого прикладу з пакетом застосунку, накладенням налаштувань і хуком увімкнення служби використайте `pib init my-image --example custom-image`. [Покроковий приклад](palette-image-builder-example.md) показує весь процес; CI збирає той самий збережений у репозиторії `image.yaml` на обох архітектурах. Приклад входить до контейнера, тому клонувати репозиторій не потрібно.

## 3. Один раз налаштуйте підписування

Для розробки створіть тестовий CA та дані підписування:

```bash
pib keys init --cn 'My Company Development'
```


Після налаштування перемістіть `keys/ca.key` у захищене офлайн-сховище. Сертифікат підписування та його приватний ключ залишаються в `keys/`; створений `.gitignore` виключає приватні ключі й результати збирання. Зробіть захищену резервну копію. Наявні плати довіряють вашому CA, тому зберігайте його при переході до іншого проєкту або платформного випуску.

Для виробництва використовуйте дані підписування своєї організації. Дивіться [зовнішні ключі й оновлення сертифікатів](palette-image-builder-reference.md#signing). Контейнер не містить виробничих ключів підписування SiMa.

## 4. Налаштуйте образ

Для першого збирання створіть у редакторі `overlay/etc/motd`:

```text
My custom Modalix image
```


Файли з `overlay/` зберігають дозволи та належать root у готовому образі. Накладення застосовується до встановлення пакетів, тому пакет може замінити файли поза `/etc`. Для змін після встановлення використовуйте хук.

Щоб встановити застосунок як пакет Debian:

```bash
cp /path/to/my-app_1.0_arm64.deb custom-debs/
pib sign-debs
pib verify-debs
```


Додайте до `image.yaml` **назву пакета**, а не ім’я файла:

```yaml
packages:
  add: [my-app]
  remove: []
```


Архітектура пакета має бути `arm64` або `all`. Заміна ядра, вилучення пакетів, увімкнення служб і власні сценарії оновлення описані в [довіднику з налаштування](palette-image-builder-reference.md#customization).

## 5. Зберіть підписане оновлення

```bash
pib build --sign
```


Команда збирає образ, підписує SWU налаштованим ключем і перевіряє підпис, хеші вмісту та маніфест збирання. Зазвичай це триває кілька хвилин залежно від хоста й мережі. Результати з’являються в `out/`:

| Результат | Призначення |
|---|---|
| `*.swu` | Підписаний пакет оновлення |
| `*.unsigned.swu` | Пакет для окремого етапу підписування |
| `*.img.gz` | Стиснений образ диска для початкового налаштування/відновлення |
| `*-boot0.be` | Відповідний компонент tRoot |
| `*.manifest.json` | Версії й джерела пакетів та походження завантажувальних компонентів |
| `*.cdx.json` | Перелік складових ПЗ у форматі CycloneDX |
| `SHA256SUMS` | Контрольні суми артефактів |

Щоб перевірити повторно без пошуку назв файлів:

```bash
pib verify
```


Для CI або окремої системи підписування виконуйте `pib build`, `pib sign` і `pib verify` незалежними кроками. `pib sign` та `pib verify` вибирають версію поточного `image.yaml`, навіть якщо `out/` містить старіші версії.

Перед наступним збиранням збільште останню частину `version` у `image.yaml`, наприклад з `3.0.0.1` до `3.0.0.2`. Повторне збирання тієї самої версії замінює її результати, включно з уже підписаним SWU. Плати застосовують політику версій образу.

## 6. Підготуйте розгортання

Збирання та перевірка пакета не змінюють плату. Перед розгортанням:

- Налаштуйте доступ першого запуску, якщо записуєте образ на нову плату. Типово `root` і `sima` заблоковані; під час оновлення можуть зберегтися наявні облікові дані. Дивіться [доступ до плати](palette-image-builder-reference.md#board-access).
- Налаштуйте довіру до CA через затверджену процедуру підготовки плати. Заводська плата не починає автоматично довіряти новоствореному CA.
- Використовуйте правильний шлях: SWUpdate для `.swu`, а для `.img.gz` і потрібних завантажувальних компонентів — перевірену процедуру запису/відновлення платформи.

Команди оновлення через SSH наведено в розділі [встановлення SWU](palette-image-builder-reference.md#installing-an-swu). Перед виробничим використанням перевірте власний образ на відновлюваній платі для розробки.

## Усунення несправностей

- **Немає доступу до loop/device-mapper:** запустіть `pib doctor`. Запускач надає необхідні привілеї, але Linux-хост Docker має підтримувати відповідні пристрої.
- **Помилка налаштування ARM64 на x86:** PIB автоматично реєструє вбудований емулятор. Перевірте, чи дозволений привілейований доступ binfmt у Linux-рушії Docker.
- **Збирання перервано:** спочатку зупиніть збирання, перевірте залишкові ресурси через `pib clean`, потім видаліть їх командою `pib clean --yes`. Очищення може зачепити інші проєкти PIB на тому самому хості Docker.
- **Помилка пакетів/bootstrap:** перевірте `configs/images/mmdebstrap.log`. Репозиторії пакетів мають бути доступні під час збирання.
- **Новий платформний випуск:** створіть новий проєкт відповідним контейнером, збережіть наявний CA та перенесіть сумісні пакети й налаштування. Дивіться [довідник з оновлення](palette-image-builder-reference.md#new-platform-release).
